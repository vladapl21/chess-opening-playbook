# Notes for working on this repo

The plan for the next phases is in [ROADMAP.md](ROADMAP.md). Read it first.

## Build and test

- `make build` (or the five scripts in `pipeline/`: both books, the course, `plan_lines.py`, `assemble.py`) rebuilds both books, the course, the plans and the page. It needs the engine paths from the README: `STOCKFISH`, `MAIA_WEIGHTS`, `LCZERO_TRAINING`. The engine caches in `data/cache/` make rebuilds fast and reproducible (`plan_cache.json` holds Stockfish's line from every line end; a new line end needs the engine once). Check that a rebuild reproduces the committed files.
- `pipeline/assemble.py` writes two pages from `app/template.html`:
  - `data/build/playbook.html` for the claude.ai artifact (no accounts, uses the artifact's own database);
  - `docs/index.html` for GitHub Pages (accounts through Supabase when `app/site.json` has a URL and key).
- Tests drive the real page in Chromium (Playwright, pre-installed): `tests/e2e_white.py`, `e2e_black.py`, `e2e_sandbox_switch.py`, `e2e_course.py`, `e2e_accounts.py`, `e2e_engine.py`, `e2e_versions.py`. `tests/e2e_daily.py` covers today's five, the streak, badges, settings from another device and the explore board's history; `tests/e2e_shop.py` the levels, the daily shop and the locker; `tests/e2e_recap.py` the monthly recap with chess.com stubbed (three months of `data/games/aqua_alpaca.pgn`, re-dated); `tests/e2e_artifact_sync.py` the claude.ai copy on two devices (a stand-in for the artifact database); `tests/e2e_library.py` the end of the course, the library and the deep dives (over local HTTP); `node tests/nudge_check.mjs` the reminder-email rules. `tests/e2e_shell.py` and `tests/e2e_onboarding.py` cover the shell and a new visitor, `tests/e2e_skills.py` the skill units and the engine's numbers, `tests/e2e_packs.py` the systems, `tests/e2e_tour.py` the tour, `tests/e2e_review.py` the last three games (chess.com stubbed, the real engine) and the coach's word when a game left the book, `tests/e2e_marks.py` the marks on the moves (in lessons, and on the board during a drill and a Sandbox game), the opening names, the move numbers on the pieces and the lesson board that takes moves, `tests/e2e_sandbox_switch.py` the Sandbox with both colours, and `node tests/ideas_check.js` the move explainer (known positions, then every book move; `--all` prints every line it writes). `e2e_packs.py`, `e2e_course.py`, `e2e_shell.py`, `e2e_onboarding.py`, `e2e_tour.py`, `e2e_review.py`, `e2e_marks.py` and `e2e_recap.py` (all but the first two on the website's own page, `Site(docs=True)` in `tests/serve.py`) run over local HTTP: headless Chromium sometimes drops a `file://` page's storage across a scripted reload. Run the suites one at a time and with no engine job beside them: they are timing-sensitive on two CPUs. Screenshots go to `tests/out/` (ignored). Console errors that mention `ERR_TUNNEL_CONNECTION_FAILED` are the proxy blocking Google Fonts and the supabase-js CDN, not the app.
- The engine is a web worker, so it can't start from a `file://` page. `tests/serve.py` serves the build over local HTTP with `engine/` beside it; `e2e_engine.py` and the engine screenshot use it.
- `make check` runs the engine and wording checks on the Black book and on the White book's packs after the first (the London and the English; `pipeline/check_white.py`, the same report from White's side, and with lesson or part ids it checks those whatever their pack: `B-RARE` and `B-MISS` are information, `W-LOSS`, `ILLEGAL` and `ENDS-ON-BLACK` need a look; a line with a move tagged `warn` shows a mistake on purpose and is skipped). `lint_notes.py` reads the London's notes too. `W-RARE` and `W-MISS` lines are information, not failures; `B-LOSS`, `ILLEGAL` and `ENDS-ON-WHITE` need a look. Both checks read the lines as the build plays them on (`deepen.apply`, from the cache), and a move they flag is measured again against the engine's own move one ply on at the same depth, so the book's move being the engine's best is never a loss. `B-LOSS bsi-open-c3` is a choice: the book declines a pawn offer the engine would take, and stays level. The first White pack is hand-built and not in the default run (`check_white.py 14 <its parts>` lists the Møller's pawn offer, a long trap line and four lines that end on Black's move on purpose).
- `pipeline/lint_claims.py` checks both books for the same position answered with two different moves, for pin wording with no pin on the board, and for labels that say a move guards or hits a piece when it doesn't. `assemble.py` runs it and stops on any finding, so fix the content, never the check.
- `pipeline/lint_counts.py` works out every count the README quotes from the built books: the At a glance table (the house playbook: the first system in every slot), the course and library totals, the rows of the Systems table, and the shop's counts (read from `app/product.js`). `assemble.py` runs it after the page is written and ends with exit code 3 when a number is stale; `python3 pipeline/lint_counts.py --write` puts them right. A change that adds lines, lessons, units or a system ends with that command. A new kind of count in the README gets a row (`ROWS`) or a pattern (`expected`) there.
- `data/line_versions.json` holds `{line id: [version, hash of its moves]}` and is committed (the page's `VER` reads every system's lines, `D.full`, so progress kept in a system that isn't in play is not called changed). `assemble.py` bumps a version when a line's moves change. Nothing on the page says so, and nothing will: a record made on an older version stands as it is (its box, its due date) and takes the new version the next time the line is played (`Prog.record`; `Prog.stale` is internal, and `changedNote` is empty). A rebuild that changes no moves must leave the file untouched. Ids of removed lines stay in it, so a reused id starts on a new version.
- The site build opens on the welcome screen for a visitor without games. The older suites test the hand-built playbook, so `launch()` in `tests/e2e_white.py` marks every context as the house player; `launch(p, house=False)` starts as a new visitor (`e2e_onboarding.py`, the last part of `e2e_accounts.py`). `launch()` also marks the tour as taken (`playbook-tour` in localStorage) so it doesn't cover the page; `launch(p, tour=True)` lets it start by itself. A test that seeds its own progress must not be skipped by that mark (see the seed in `e2e_versions.py`).
- `docs/img/review.png` is made by `readme_shots.py` from reviews seeded with what `e2e_review.py`'s engine found. `docs/img/welcome.png`, `findings.png` and `choices.png` are copies of `tests/out/o_start.png`, `o_findings.png` and `o_choice_system.png` from `e2e_onboarding.py`.
- README images: `FONTS_DIR=<google/fonts ofl folder> python3 tests/readme_shots.py` (needs `barlow`, `barlowcondensed` and `jetbrainsmono` from a sparse checkout of google/fonts).

## Deploy

- Work on a branch, push it, open a PR with `gh api` (GraphQL is blocked here), and merge it with `gh api -X PUT repos/vladapl21/chess-opening-playbook/pulls/<n>/merge`. GitHub Pages serves `main` → `/docs`.
- The claude.ai artifact is https://claude.ai/artifact/5RHAUYcSDGBWjJa2QWPaxi. `data/build/playbook.html` has no document skeleton: wrap it (doctype, charset and viewport metas, the small reset the live page starts with) and publish the result as `index.html` of that artifact. Its two engine files (`engine/…`) and its capabilities (db, user) are kept when only `index.html` is sent.
- The proxy blocks Supabase hosts from this environment. Account features are tested against `tests/fake_supabase.js`; the real project is checked in the browser.

## Where things live

- `app/template.html` is the whole app. The engine code sits in one block before the boot code: `Engine` (the worker and UCI), `Ana` (one analysis per position, kept for the session), `moveWords` (engine moves in plain words), `EngineUI` (card, arrows, eval bar) and the explore view (`exploreFrom`, `renderExplore`).
- `app/analyze.js` is the game analysis (PGN in, profile out). No DOM, so `node tests/analyze_check.js` runs it on `data/games`. It gets the whole library (`D.full`) but reads each game against one pack per slot (`homePacks`: the picks passed in, else the pack the player's own games fit when the library has it, else the first system; kept as `P.home`), so a move that only another system plays still counts as leaving the book. The chapter a position belongs to is counted the same way, over the chapters in play (`indexBook(D, ok.off)`): two systems of one slot may both start from a position, and it still belongs to the one in play (`analyze_check.js` fails when a new system takes positions away from the house's chapters). The games as read stay with a fresh profile for the visit (`P._games`, never stored): when a new player picks a system other than the one their games fit, `Analyze.again` makes the profile again for those picks at once. The monthly recap passes the packs in play (`packsNow`). A game is replayed with `sanMove` (the SAN read by hand, each candidate piece tried by its squares: about nine times quicker than the chess library's own SAN reader, which froze a phone for seconds on a month of games), and `Analyze.newest(raw, user, n)` replays only the newest games asked for; `run` yields every four games so the page keeps responding.
- The daily habit lives in the template (`Daily`, `dailyNext`, `todayHTML`, `dailyGo`; `d.days` in the progress record) and in `product.js` (`BADGES`, `Badges`, `profileHTML`, the coach's medal). `Prog.save` is wrapped there to check for new badges. Settings are kept in `d.set` with a time stamp (`setSetting`, `adoptSettings`). The flame's colour follows the streak (`FLAMES`, `flameTier`: a new one at 5, 10, 20, 30, 50 and 100 days; `data-flame` on the root picks the `--fl<n>` tokens, and a streak of zero stays grey).
- **Anything new that a player sets or earns must follow them to every device.** Put it in the progress record (`Prog.d`), give it a merge rule in `mergeProg` (union, max, or newest by its own time stamp; add its key to `KNOWN`), and add it to the two-device checks in `e2e_accounts.py` and `e2e_artifact_sync.py`. Never keep it only in localStorage. Saves read the stored copy and merge before writing (`Cloud.write`, `Prog.push`).
- The shop lives in `product.js` (`SHOP`, `Shop`, `renderShop`, `gearSVG`). The fit: `SPOT[who].head` places a hat (x, the line its rim is pulled down to, tilt, size) with a shadow under the rim (`.g-seat`; not for `HAT_LOOSE`), and `hatBox` gives the picture the room that hat needs (`HAT_H`, plus the lifted side of a tilted brim). Everything worn at the neck is drawn along `NECKLINE[who]` (`neckCurve`, `neckSVG`): a scarf is the line as a band with its knot and tail, a lei beads on it, a chain hangs from its ends, and a tie, a bow or a medal (`KNOTS`) sits at one point of it. The knight is seen from the side, so what goes round its neck is cut to its outline (`KN_BODY`, `KN_MANE`; a `clipPath` with its own id per picture, `kc<n>`). A shop card shows the piece by itself in the colour worn, zoomed on its slot (`.ipv.z-<slot>.zk-<who>`); the outfit is on `.mannequin`. A new piece is checked on all three coaches (`e2e_shop.py`'s fit checks). It opens at level 5 (`SHOP_AT`). Tokens are computed (badges + every third day in a row + one per level from 5 on − prices of what is owned), never stored. The shop's shelf is a daily shop: `SHELF` is how many pieces of each kind a day's shelf holds, and every priced piece has a rarity (`rar`: common, rare or epic; legendary pieces come only from crates). `Shop.on(date)` deals each kind from a fixed deck (`Shop.deck`: three rounds of the commons with a third of the rares in each, so a rare comes up about a third as often) over the priced pieces not owned before that day (a piece with `needs` joins once its badge is earned), and on one day of each week one epic takes a place on the shelf (the epics in turn, `epics[week % n]`). `Shop.today()` is what can be bought, and `lockOf` answers `gone` for everything else. The page is the switch between the daily shop and the locker (`S.shopTab`) with the timer beside it (`#dropT`, `Shop.endsIn()`), then the shelf with the crate as a banner under it (`crateBanner`: Buy a crate, and What's inside, which opens the crate's own page, `S.shopTab === 'crate'`, with the odds and every piece); under 860px the coach sits small beside the tokens (`.shopside` as a grid) so the shelf is on a phone's first screen; the locker has what is owned, by kind, and the badge pieces not yet earned. A piece bought today stays on the shelf as owned (`.item.owned`, the greyed `.ownedbtn`), and buying is a moment (`shopFx`: the card's pop, `burst` for the confetti, the mannequin's hop, the `buy` sound). Crates: the pieces with `crate: 1` and a rarity (`rar`; `RAR` has the odds) are never on the shelf; `Shop.openCrate()` costs `CRATE_PRICE`, draws one that isn't owned (`crateRoll`: the rarity by its odds among those with pieces left, then a piece of it) and puts it in `own`, so the pieces owned count the crates paid for (`spent`). `crateOpen()` draws first and shows after: the crate floats and glows until it is tapped (`.cratewait`, `[data-cratetap]`; it can't be closed before, so nothing bought goes unseen), then the reel (`.strip` slides under `.reelmark` and stops on the piece, a `tick` per piece passed), then the piece (`.prize`, `win` by rarity), with Skip, Wear it and Open another. Crate colours are skins like the others (`SKINS`, `--sk-*`); auras are a slot of their own (`AURAS`, drawn behind the coach in `knightSVG`, the same for all three). Rarity colours are `--rar-*`. No heading, day names or sub-lines on the shelf: the timer says all of it. Gear colours are CSS tokens (`--gear-ink`, `--sk-*`).
- Levels: `XP` and `Level` in the template (points are computed from the record, never stored; a line's `ps`/`pc` carry the points of a version its moves left behind) and `Lv` in `product.js` (the chip, the floating points, the level-up card, held in `Lv.pending` while a line is played). The chip's number sits in ink inside a ring that fills toward the next level (`--p` on `.lvc`). `d.lvl` is the highest level celebrated, merged as the max.
- The header is one grid: the brand and the player's things (`.corner`: level, streak, settings, account) on the first row, the tabs on a row of their own. `.corner` sits inside the header and nothing is positioned over it. `e2e_shell.py` checks for overlaps from 360 to 1920px.
- There is no White/Black switch, and none comes back. `SIDE` is still the book on the page, and `useSide(side)` loads the other one and keeps the view: a click inside `[data-bk]` (a tile, a row, a chip of that colour's book) calls it, and so does `render()` for a drill or a practice game under way, which carries its colour (`D.side` on every drill state; `S.drillState`, `S.sbState`, the Sandbox's session and the Drill filter are not kept per book). Pages that show both books read the other one through `withBook(s, fn)`: Your games (`.gside[data-bk]`, `colHead`) and the Drill page (`bookLines(s)`, `eligibleLines()` over both, `S.dfilter.ch` is `all` or `<side>:<chapter>`, `nextSmart` gives `{id, s, why}`). The Drill page's list of every line folds by opening (`details.mch`, `S.mopen`; an opening's rows are drawn when it is opened): two books are too long to list flat. A new page that lists openings or lines lists White's and then Black's.
- Marks on the moves: `markOf(idx)` in the template (kept per node in `_mk`, cleared by `setPerspective`). The other side's moves: the share of the point the move hands over, from the stored engine numbers (`shareOf`, `cpOf`; 9% an inaccuracy `slip`, 16% a `mistake`, 28% a `blunder`), a move into a forced mate, and the notes' own tags (`blunder`; `mistake` is at least an inaccuracy). Yours: `key`, the answer to a mistake or a blunder or to a move the notes call a mistake; a `warn` move reads as a mistake. `MARKS` has the words, `markWords` the sentence on the move card, `MARK_SIGN` the signs (`!`, `?!`, `?`, `??`; `markGlyph` draws them), `--mk-*` the colours (blue, amber, orange, red: the family other sites use, not their values, in both themes). In a lesson: `o.mark` on the study board through `nodeBoardOpts` (never on a small board), the chip on the move card, `markIcon` in the list of moves and `markLegend` when the line has any. Live, in a line drill and a Sandbox game: `liveMarks(idx, word)` gives `o.marks` to `renderDrillBoard` (the move just played, and the move before it while its piece still stands, so a key move keeps its badge through the reply); the word pill beside the badge (`g.mkl`) shows on the first drawing of a move only (`D.mkAt`); `markChipIn` puts the chip in the panel's lines, and `sbFeed` marks the Sandbox's list as it grows. Checkpoints and missed-shot puzzles get none. The old `key` tag is quiet (`QUIET_TAGS`): it sat on half the book's moves.
- The order of your moves is on the lesson's board: `orderNums(line, i)` gives each piece of yours the number of the move that put it there (`o.nums` in `boardSVG`), on by default and kept as the setting `nums` (`SET.nums`, the Move numbers switch beside the engine's; it follows the player like every setting). `orderOf` compares a line with the main line of its chapter's first lesson: the shared moves that keep that order stay, the others are `odd: 'swap'`, and a move the main line doesn't have before the last shared one is `odd: 'new'` (only with three or more shared moves); an odd move's number is purple (`.onum.odd`, `--ord`) with one line under the board (`.onote`). There is no strip of small diagrams any more: it was more to decode than the board. Game reviews have no numbers. A line drill knows an order slip: `laterInLine(D, u)` is how many of the player's moves later the line plays the move tried, the panel then says `earlyHTML` (that move comes N moves later; it doesn't name the move that is due), `D.slipOrd` keeps it by move, and `Coach.lineNote` says the order slipped, with See the order.
- A lesson's board takes moves for whichever side is to move (`wireStudyInput`, `studyTry`, `studyBoard` redraws the board alone): the line's own next move steps on, a move with a book line behind it opens that line at that move (`linesByNode`), and any other legal move opens the explore board with the move made and the engine on. One engine readout: where a page has the verdict and the depth under its board (`h.text` of `EngineUI.attach`), `engineCardHTML` leaves them out of the card.
- Material beside the big boards (lesson, drill and Sandbox, explore): `materialOf(fen)` and `matUpdate(el, fen, flip)` fill two thin rows, `.mat.top` and `.mat.bot`, with the pieces each side has taken and `+N` on the side that is ahead. The rows stand in the page templates (so nothing shifts) and are filled on every drawing of the board (`studyBoard`, `renderDrillBoard`, `exBoard`); a board drawn elsewhere gets them made on its first drawing.
- Piece animations and sounds are settings (`anim`, `animk`, `snd`, `sndk` in `SET_DEF`/`SET_KEYS`; `SET_BOOL` lists the switches): `animSpec(dx, dy, kind)` gives the keyframes and timing of a slide (`ANIMS`: slow, medium, fast, natural, arcade, dynamic) and `slide(el, dx, dy, kind, cap)` runs it, for `animateMove` and for the little board in Settings (`animPreview`, a capture every second run). Natural lifts the piece with a shadow, Arcade overshoots, Dynamic arcs and tilts; `fxRun` adds what lands with them (`a.fx`: after-images `.fx-ghost`, a ring `.fx-ring`, sparks `.fx-spark`, and on a Dynamic capture a shake of the board; `_blast[id]` from `boardSound` says whether the move took something). A piece that scales or turns does it around a point in board units (`transform-box: view-box` with the origin at the piece's foot): `fill-box` measures from the board's corner on an SVG `<use>`, and the piece flew off the board. `Sound.play(name)` makes every sound in the browser, sample by sample (no files; `SND`: `mode`, `burst`, `pulse`, `room`; `SND_THEMES`: soft, the default, then wood and arcade). Every sound is levelled to the same loudness (`loud`: a K-weighted 60 ms window; `LEVEL` per sound), rendered once per theme, sound and level and kept as an AudioBuffer (`Sound.bufs`; three takes of a move and a capture so they don't sound the same every time): `boardSound(id, fen)`, called from `matUpdate` on every drawing of a big board, plays a move, a capture, castling or a check when the position is one move from the last one drawn there, a wrong move buzzes in `renderDrillBoard`, a clean line chimes in `finishLine`, and the shop has its own (`buy`, `tick`, `win`). `Sound.last` and `Sound.n` are there for the tests (headless Chromium never starts the audio); `e2e_shell.py` renders every sound and checks the levels match within 0.6 dB.
- A move the player makes never slides: their own moves call `renderDrillBoard()` with no move to animate (line drills, Play along, the Sandbox, checkpoints, the review drill, the set-up board in both directions, `exPush(u, true)` on the explore board). Only the other side's reply and stepping through a line slide.
- Play along: `startGuided(lineId, unitId)` runs a lesson's line on the drill board as a drill with `guided: true`. The move to make is the green arrow on every one of the player's turns, `guidedPanelHTML` is the coach's card beside the board (what the other side played, the move, and why in one line), and a wrong move just doesn't go (no `mistakes`, no `slipAt`). The main line played to its end marks the lesson studied (`markSeen`, its points); no line record is made. A lesson also counts when stepped through to its last move in the study page (`S.stepped`); jumping there doesn't count. `unitNext(U)` is the one action that leads on in a unit: a played-along line not yet clean from memory, then the next lesson to play along, then the practice games, then the checkpoint. A unit drill or play-along stays under the Course tab (`setTab`) with crumbs back to the unit, and a unit drill with a slip leads with Again.
- What a move does, read from the board: `app/ideas.js` (no DOM; chess.js 0.x; inlined by `assemble.py` at `/*__IDEAS__*/`). `Ideas.of(fen, uci, {me, prev})` gives at most two lines, the most important first (`PRI`): a win, a fork, a check that wins something, a mate threat made or stopped, a threat made or stopped, an uncovered attack, a guard taken away, a pin, a trade, castling, the aim at f7 or f2, a piece left loose, the center, a line opened, a piece brought out. `Ideas.punish(fen, uci, {me, words})` is the best answer to a move off the book (`kind`: mate, take or fork; `gain`; `took`, what the move itself took, so a fair trade is never called a mistake; `lines`), `Ideas.reply` why a known answer works. In the template: `ideaOf(idx)`, `ideasBeyond(idx)` (what the note doesn't already say: `IDEA_SAYS`, `IDEA_TACT`), `moveWhy(idx, max)` (the note first, then the board), `punishOf`, `punishHTML`, `whyHTML`. They feed the drill panel (`D.feed`: the name of the move just made and the other side's move with its idea; `D.msg` on a slip: the punishing answer, and on the second miss why the book's move is the move), Play along, the move card of a move with no note, the Sandbox, a practice set's refutation and the explore board's last move. Its words follow the house rules (plain words from the player's side, no notation): a new phrase gets a known position in `ideas_check.js`.
- The tour: `Tour` at the end of `product.js`. Three steps and no more (`Tour.build()`: pick a coach, play the green arrow's move on the board, the course's button that always leads on); everything else is said where it is met, by the coach's tip on the first visit to each place (`Coach.tip()`, once per place: `Coach.once('tab-' + place)`, kept in localStorage `playbook-coach`; each part of Your games with a tip of its own is a place, `games-last`, `games-recap`). A step has `h`, `say`, `at` what to light, `go` what to set up, `act` a move to wait for with its `auto`, `skip`, `pick` for the coach (skipped when a coach was already picked, `SET.ts.who`, and on a replay). It starts by itself (`Tour.boot` in `start()`) for a player who hasn't taken it, never for `PERSONA === 'new'`, on the onboarding views or with Settings open; a new player gets it on the reload into their playbook. No close button and no Fast forward: on a first run Next is held for a moment behind a bar (`Tour.HOLD`, at most 1.4 s; `held`, `holdLeft`; the Enter key waits too; no bar on a step come back to), Show me plays the step's move, Back goes a step back, Escape says how short it is. Taken again from Settings (`Tour.replay`) there is no bar and Escape closes it. Finishing a first run marks the course's tip as said (`Coach.mark('tab-course')`: its last step just said it). On a phone the card is a sheet docked to the bottom of the screen (to the top when its target is down there: `.attop`), the ring keeps to the part of the screen the sheet leaves free, and `html.twon` gives the page room to scroll so a target can always sit clear of the sheet. Lines it starts carry `tour: true` and record nothing (no `Prog.record`, no `markSeen`, no points). Taken is `Prog.d.tour = {done}` (merged as the earliest, in `KNOWN`) plus `playbook-tour` in localStorage; Settings → Take the tour again is `Tour.start(true)` and ends on the view it started from. Its classes use the `tw` prefix (`.tour` and `.tring` were taken). `e2e_tour.py` checks the three steps, how few words they have (nothing about the shop), and a tip of one or two short lines on the first visit to every tab, said once.
- The last three games: `Review` in `product.js`, a part of Your games (`S.gseg === 'last'`, house and personal) with a pointer on the Drill page (`drillCard`). On the website it reads the newest games through `Recap.read` (`check`, at most every `RG_EVERY`, and Check now); any copy takes a pasted PGN (`add`, which asks for the side when neither player is the account). Three are kept in `d.rg.g` (newest `added` first; merged per game in `mergeProg`: what either copy worked out, the earliest `added`, the drill counts with more runs; `rd()` reads without creating the key, `st()` writes). Each review: `u` the moves, `at`/`by` where it left the lines in play (`walk`, over `inBook(s)`: the nodes on `BOOKS[s].lines`; `by` is `opp`, `me` or `end`), `ln` the engine's answer when the opponent left the book, `mk` the first move that lost 150 or more (depth 10, checked again at 14; `0` when there is none), `d` the drill runs (`o` and `m`: [runs, clean, last]). The engine part (`work`) runs only while the part is on screen and stops when it isn't, so it never takes the engine from a lesson. ## House rules for the app

- The house playbook (the artifact build, and accounts with progress from before personal playbooks) must look and behave as before. Anything written for other players goes through `PERSONA`.
- The coach never speaks while a drill, practice game or checkpoint is being played, and never hints at a move. A badge earned then waits in `Badges.queue`. Play along is the one place the move is shown, by design: the arrow and the coach's card beside the board, never the bubble. The tour is the one place the coach leads the player through the app; while it runs the bubble stays quiet.
- A drill explains, but doesn't give the move away: the other side's move comes with its idea, and a slip with the answer that punishes it. The book's move is named only on the second miss, with the arrow.
- No game counts in what a new player reads about bringing games in ("connect your account"). The 200-game bar (`NEED` in `product.js`) is checked, not announced.
- One position, one move, inside every combination of packs a player can hold. If two move orders reach the same position, the book plays the same move in both. Before changing a line, look for the position in the other lessons (`lint_claims.py` reports the conflicting paths).
- One order per setup. The d-pawn setup comes out in the order given in the README ("One setup, one order"). Where a line has to leave that order, the note at that move says why.
- A label says only what is on the board. "Pin" needs a piece that can't or shouldn't move because of what is behind it; a bishop coming at a knight with a pawn behind it is "Bishop comes at your knight". "Guards" and "hits" are checked the same way.
- The repertoire is "your book" in what the player reads (not "your study", "the guide" or "your prep"), and nothing on the page is written for the house player alone unless it goes through `PERSONA`: there is no footer line about where the playbook came from. Your games has no header with a count of games: totals go out of date, and no text quotes one ("in your 76 with White"). A count the page shows is counted from the book on the page (the Sandbox's lines met: `sbPool()`), never written down.
- A real name before a description. Where an opening, a gambit or a named line has a name (`data/openings`), the tiles, parts, lesson and line titles and the other side's choices use it (`content/opening_names.py`); labels that explain a move ("Knight hits your e-pawn") stay. Every board in study, drills, the Sandbox and the explore board shows the position's opening name.
- The tour stays three steps. A new place gets a first-visit tip from the coach (`Coach.tip()`), one or two short lines, not a tour step.
- As few words as the screen can take. Before adding text, ask whether something on the same screen already says it (a button, a count, a heading, the board) and whether anyone would miss it; if not, leave it out. A drill slip gets one thing (the answer that punishes it; on the second miss, why the book's move is the move), the coach's note after a line one line (the move that caught you and the line's move there), a step of a unit its name, its count and its button, a setting its name. While a line is on the drill board the page is the board and its panel, nothing else (the Today card and the line picker wait: the panel's own button says which of today's five comes next).
- No chess notation in anything the user reads. The squares f7 and f2 are the only exception, with the four signs on the marks (!, ?!, ?, ??). Arrow and move data inside the code is fine. This covers what the engine says too: its moves go through `moveWords`.
- Marks show in lessons, and on the board as the moves are played in line drills and Sandbox games: the sign at the corner of the piece's square, the word beside it for a moment. Checkpoints and missed-shot puzzles show none: they ask for the move.
- A move the player makes lands at once. Only the other side's reply slides.
- No White/Black switch. Every tab holds both books, the Sandbox plays both colours in turn when everything is picked, and anything opened loads its own book.
- Say a thing once, in a plain phrase. No headline made of two fragments joined by a comma ("Two drops, gone at midnight", "Same setup, same plan"), and no line that repeats what a heading, a timer or a number on the same screen already says. Lists of moves in a plan ("Take, then the big center") are fine.
- The engine never shows during a drill (Play along included), a practice game or a checkpoint. It comes on when they end, and it is always available in lessons and game reviews. In a skill unit's practice sets it opens per position once that position is answered.
- Engine numbers are from White's side for both colours (plus: White is better). Only the words are turned to the player's side.
- Every colour is a CSS token defined for both light and dark themes. Check phone width (390px) for sideways scrolling.
- Progress records are shared between the books, so line, puzzle and lesson ids must never collide (`assemble.py` asserts this).
- Record counts quoted in the course text come from all 200 games; the books' own stats come from the original 149.
