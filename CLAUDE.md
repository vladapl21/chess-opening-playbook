# Notes for working on this repo

The plan for the next phases is in [ROADMAP.md](ROADMAP.md). Read it first.

## Build and test

- `make build` (or the five scripts in `pipeline/`: both books, the course, `plan_lines.py`, `assemble.py`) rebuilds both books, the course, the plans and the page. It needs the engine paths from the README: `STOCKFISH`, `MAIA_WEIGHTS`, `LCZERO_TRAINING`. The engine caches in `data/cache/` make rebuilds fast and reproducible (`plan_cache.json` holds Stockfish's line from every line end; a new line end needs the engine once). Check that a rebuild reproduces the committed files.
- `pipeline/assemble.py` writes two pages from `app/template.html`:
  - `data/build/playbook.html` for the claude.ai artifact (no accounts, uses the artifact's own database);
  - `docs/index.html` for GitHub Pages (accounts through Supabase when `app/site.json` has a URL and key).
- Tests drive the real page in Chromium (Playwright, pre-installed): `tests/e2e_white.py`, `e2e_black.py`, `e2e_sandbox_switch.py`, `e2e_course.py`, `e2e_accounts.py`, `e2e_engine.py`, `e2e_versions.py`. `tests/e2e_daily.py` covers today's five, the streak, badges, settings from another device and the explore board's history; `tests/e2e_shop.py` the levels, the shop, today's drops and the locker; `tests/e2e_recap.py` the monthly recap with chess.com stubbed (three months of `data/games/aqua_alpaca.pgn`, re-dated); `tests/e2e_artifact_sync.py` the claude.ai copy on two devices (a stand-in for the artifact database); `tests/e2e_library.py` the end of the course, the library and the deep dives (over local HTTP); `node tests/nudge_check.mjs` the reminder-email rules. `tests/e2e_shell.py` and `tests/e2e_onboarding.py` cover the shell and a new visitor, `tests/e2e_skills.py` the skill units and the engine's numbers, `tests/e2e_packs.py` the systems, `tests/e2e_tour.py` the tour, `tests/e2e_review.py` the last three games (chess.com stubbed, the real engine) and the coach's word when a game left the book, `tests/e2e_marks.py` the marks on the moves and the strip of your moves in order, and `node tests/ideas_check.js` the move explainer (known positions, then every book move; `--all` prints every line it writes). `e2e_packs.py`, `e2e_course.py`, `e2e_shell.py`, `e2e_onboarding.py`, `e2e_tour.py`, `e2e_review.py`, `e2e_marks.py` and `e2e_recap.py` (all but the first two on the website's own page, `Site(docs=True)` in `tests/serve.py`) run over local HTTP: headless Chromium sometimes drops a `file://` page's storage across a scripted reload. Run the suites one at a time and with no engine job beside them: they are timing-sensitive on two CPUs. Screenshots go to `tests/out/` (ignored). Console errors that mention `ERR_TUNNEL_CONNECTION_FAILED` are the proxy blocking Google Fonts and the supabase-js CDN, not the app.
- The engine is a web worker, so it can't start from a `file://` page. `tests/serve.py` serves the build over local HTTP with `engine/` beside it; `e2e_engine.py` and the engine screenshot use it.
- `make check` runs the engine and wording checks on the Black book and on the White book's packs after the first (the London and the English; `pipeline/check_white.py`, the same report from White's side, and with lesson or part ids it checks those whatever their pack: `B-RARE` and `B-MISS` are information, `W-LOSS`, `ILLEGAL` and `ENDS-ON-BLACK` need a look; a line with a move tagged `warn` shows a mistake on purpose and is skipped). `lint_notes.py` reads the London's notes too. `W-RARE` and `W-MISS` lines are information, not failures; `B-LOSS`, `ILLEGAL` and `ENDS-ON-WHITE` need a look. `B-LOSS bv-ponziani-d5` is a known depth-14 artifact (the book's move is also the engine's best; the two searches disagree on the number). `B-LOSS bsi-open-c3` is a choice: the book declines a pawn offer the engine would take, and stays level.
- `pipeline/lint_claims.py` checks both books for the same position answered with two different moves, for pin wording with no pin on the board, and for labels that say a move guards or hits a piece when it doesn't. `assemble.py` runs it and stops on any finding, so fix the content, never the check.
- `pipeline/lint_counts.py` works out every count the README quotes from the built books: the At a glance table (the house playbook: the first system in every slot), the course and library totals, and the rows of the Systems table. `assemble.py` runs it after the page is written and ends with exit code 3 when a number is stale; `python3 pipeline/lint_counts.py --write` puts them right. A change that adds lines, lessons, units or a system ends with that command. A new kind of count in the README gets a row (`ROWS`) or a pattern (`expected`) there.
- `data/line_versions.json` holds `{line id: [version, hash of its moves]}` and is committed. `assemble.py` bumps a version when a line's moves change; the page then treats older progress on that line as due ("Changed"). A rebuild that changes no moves must leave the file untouched. Ids of removed lines stay in it, so a reused id starts on a new version.
- The site build opens on the welcome screen for a visitor without games. The older suites test the hand-built playbook, so `launch()` in `tests/e2e_white.py` marks every context as the house player; `launch(p, house=False)` starts as a new visitor (`e2e_onboarding.py`, the last part of `e2e_accounts.py`). `launch()` also marks the tour as taken (`playbook-tour` in localStorage) so it doesn't cover the page; `launch(p, tour=True)` lets it start by itself. A test that seeds its own progress must not be skipped by that mark (see the seed in `e2e_versions.py`).
- `docs/img/review.png` is made by `readme_shots.py` from reviews seeded with what `e2e_review.py`'s engine found. `docs/img/welcome.png`, `findings.png` and `choices.png` are copies of `tests/out/o_start.png`, `o_findings.png` and `o_choice_system.png` from `e2e_onboarding.py`.
- README images: `FONTS_DIR=<google/fonts ofl folder> python3 tests/readme_shots.py` (needs `barlow`, `barlowcondensed` and `jetbrainsmono` from a sparse checkout of google/fonts).

## Deploy

- Work on a branch, push it, open a PR with `gh api` (GraphQL is blocked here), and merge it with `gh api -X PUT repos/vladapl21/chess-opening-playbook/pulls/<n>/merge`. GitHub Pages serves `main` → `/docs`.
- The claude.ai artifact is https://claude.ai/artifact/5RHAUYcSDGBWjJa2QWPaxi. `data/build/playbook.html` has no document skeleton: wrap it (doctype, charset and viewport metas, the small reset the live page starts with) and publish the result as `index.html` of that artifact. Its two engine files (`engine/…`) and its capabilities (db, user) are kept when only `index.html` is sent.
- The proxy blocks Supabase hosts from this environment. Account features are tested against `tests/fake_supabase.js`; the real project is checked in the browser.

## Where things live

- `app/template.html` is the whole app. The engine code sits in one block before the boot code: `Engine` (the worker and UCI), `Ana` (one analysis per position, kept for the session), `moveWords` (engine moves in plain words), `EngineUI` (card, arrows, eval bar) and the explore view (`exploreFrom`, `renderExplore`).
- `app/analyze.js` is the game analysis (PGN in, profile out). No DOM, so `node tests/analyze_check.js` runs it on `data/games`. It gets the whole library (`D.full`) but reads each game against one pack per slot (`homePacks`: the picks passed in, else the pack the player's own games fit when the library has it, else the first system; kept as `P.home`), so a move that only another system plays still counts as leaving the book. The games as read stay with a fresh profile for the visit (`P._games`, never stored): when a new player picks a system other than the one their games fit, `Analyze.again` makes the profile again for those picks at once. The monthly recap passes the packs in play (`packsNow`).
- The daily habit lives in the template (`Daily`, `dailyNext`, `todayHTML`, `dailyGo`; `d.days` in the progress record) and in `product.js` (`BADGES`, `Badges`, `profileHTML`, the coach's medal). `Prog.save` is wrapped there to check for new badges. Settings are kept in `d.set` with a time stamp (`setSetting`, `adoptSettings`).
- **Anything new that a player sets or earns must follow them to every device.** Put it in the progress record (`Prog.d`), give it a merge rule in `mergeProg` (union, max, or newest by its own time stamp; add its key to `KNOWN`), and add it to the two-device checks in `e2e_accounts.py` and `e2e_artifact_sync.py`. Never keep it only in localStorage. Saves read the stored copy and merge before writing (`Cloud.write`, `Prog.push`).
- The shop lives in `product.js` (`SHOP`, `Shop`, `renderShop`, `gearSVG`). The fit: `SPOT[who].head` places a hat (x, the line its rim is pulled down to, tilt, size) with a shadow under the rim (`.g-seat`; not for `HAT_LOOSE`), and `hatBox` gives the picture the room that hat needs (`HAT_H`, plus the lifted side of a tilted brim). Everything worn at the neck is drawn along `NECKLINE[who]` (`neckCurve`, `neckSVG`): a scarf is the line as a band with its knot and tail, a lei beads on it, a chain hangs from its ends, and a tie, a bow or a medal (`KNOTS`) sits at one point of it. The knight is seen from the side, so what goes round its neck is cut to its outline (`KN_BODY`, `KN_MANE`; a `clipPath` with its own id per picture, `kc<n>`). A shop card shows the piece by itself in the colour worn, zoomed on its slot (`.ipv.z-<slot>.zk-<who>`); the outfit is on `.mannequin`. A new piece is checked on all three coaches (`e2e_shop.py`'s fit checks). It opens at level 5 (`SHOP_AT`). Tokens are computed (badges + every third day in a row + one per level from 5 on − prices of what is owned), never stored. Items with `daily: [weekdays]` are drops: two a day, picked by the date (`Shop.on(date)`, `Shop.today()`), sold only on the shelf above the switch between the shop and the locker (`S.shopTab`); one owned before a day leaves that day's rotation. Gear colours are CSS tokens (`--gear-ink`, `--sk-*`).
- Levels: `XP` and `Level` in the template (points are computed from the record, never stored; a line's `ps`/`pc` carry the points of a version its moves left behind) and `Lv` in `product.js` (the chip, the floating points, the level-up card, held in `Lv.pending` while a line is played). The chip's number sits in ink inside a ring that fills toward the next level (`--p` on `.lvc`). `d.lvl` is the highest level celebrated, merged as the max.
- The header is one grid: the brand and the player's things (`.corner`: level, streak, settings, account) on the first row, the tabs on a row of their own; at 760px and under the White/Black switch takes a middle row and the tabs share the width. Above that, with a larger text size, the switch wraps under the brand instead of running into the corner. `.corner` sits inside the header and nothing is positioned over it. `e2e_shell.py` checks for overlaps from 360 to 1920px.
- Marks on the moves: `markOf(idx)` in the template (kept per node in `_mk`, cleared by `setPerspective`). The other side's moves: the share of the point the move hands over, from the stored engine numbers (`shareOf`, `cpOf`; 9% an inaccuracy `slip`, 16% a `mistake`, 28% a `blunder`), a move into a forced mate, and the notes' own tags (`blunder`; `mistake` is at least an inaccuracy). Yours: `key`, the answer to a mistake or a blunder or to a move the notes call a mistake; a `warn` move reads as a mistake. `MARKS` has the words, `markWords` the sentence on the move card, `MARK_GLYPH` the shapes, `--mk-*` the colours (their own, in both themes). They show in a lesson (`o.mark` on the study board through `nodeBoardOpts`, never on a small board; the chip on the move card; `markIcon` in the list of moves; `markLegend` when the line has any) and in the Sandbox's list once a game is over (`sbFeed`). The old `key` tag is quiet (`QUIET_TAGS`): it sat on half the book's moves.
- Your moves in order: `orderStripHTML(line, i)` under a lesson's board (`myMoves`, `orderOf`, `moveMap`). `orderOf` compares a line with the main line of its chapter's first lesson: the shared moves that keep that order stay, the others are `odd: 'swap'`, and a move the main line doesn't have before the last shared one is `odd: 'new'` (only with three or more shared moves). With a difference, the main line is drawn above (`.otoks.ref`) and the moves that changed places are ringed in both rows. `S.onums` (this visit only) puts each move's number on its piece (`orderNums`, `o.nums` in `boardSVG`). Game reviews have no strip. A line drill knows an order slip: `laterInLine(D, u)` is how many of the player's moves later the line plays the move tried, the panel then says `earlyHTML` (right move, wrong moment; it doesn't name the move that is due), `D.slipOrd` keeps it by move, and `Coach.lineNote` says the order slipped, with See the order.
- A move the player makes never slides: their own moves call `renderDrillBoard()` with no move to animate (line drills, Play along, the Sandbox, checkpoints, the review drill, the set-up board in both directions, `exPush(u, true)` on the explore board). Only the other side's reply and stepping through a line slide.
- Play along: `startGuided(lineId, unitId)` runs a lesson's line on the drill board as a drill with `guided: true`. The move to make is the green arrow on every one of the player's turns, `guidedPanelHTML` is the coach's card beside the board (what the other side played, the move, why, in two bullets at most), and a wrong move just doesn't go (no `mistakes`, no `slipAt`). The main line played to its end marks the lesson studied (`markSeen`, its points); no line record is made. A lesson also counts when stepped through to its last move in the study page (`S.stepped`); jumping there doesn't count. `unitNext(U)` is the one action that leads on in a unit: a played-along line not yet clean from memory, then the next lesson to play along, then the practice games, then the checkpoint. A unit drill or play-along stays under the Course tab (`setTab`) with crumbs back to the unit, and a unit drill with a slip leads with Again.
- What a move does, read from the board: `app/ideas.js` (no DOM; chess.js 0.x; inlined by `assemble.py` at `/*__IDEAS__*/`). `Ideas.of(fen, uci, {me, prev})` gives at most two lines, the most important first (`PRI`): a win, a fork, a check that wins something, a mate threat made or stopped, a threat made or stopped, an uncovered attack, a guard taken away, a pin, a trade, castling, the aim at f7 or f2, a piece left loose, the center, a line opened, a piece brought out. `Ideas.punish(fen, uci, {me, words})` is the best answer to a move off the book (`kind`: mate, take or fork; `gain`; `took`, what the move itself took, so a fair trade is never called a mistake; `lines`), `Ideas.reply` why a known answer works. In the template: `ideaOf(idx)`, `ideasBeyond(idx)` (what the note doesn't already say: `IDEA_SAYS`, `IDEA_TACT`), `moveWhy(idx, max)` (the note first, then the board), `punishOf`, `punishHTML`, `whyHTML`. They feed the drill panel (`D.feed`: the move just made and the other side's move with its idea; `D.msg` on a slip: the punishing answer, and on the second miss why the book's move is the move; `D.slipWhy` keeps the first for the coach's note), Play along, the move card's "On the board", the Sandbox, a practice set's refutation and the explore board's last move. Its words follow the house rules (plain words from the player's side, no notation): a new phrase gets a known position in `ideas_check.js`.
- The tour: `Tour` at the end of `product.js`. `Tour.build()` lists the steps (`h`, `say`, `at` what to light, `go` what to set up, `act` a tap to wait for with its `auto`, `demo`, `ready`, `skip`, `pick` for the coach). It starts by itself (`Tour.boot` in `start()`) for a player who hasn't taken it, never for `PERSONA === 'new'`, on the onboarding views or with Settings open; a new player gets it on the reload into their playbook. No close button: Fast forward runs every `auto` and demo, Show me one, Back a step. Lines it starts carry `tour: true` and record nothing (no `Prog.record`, no `markSeen`, no points). Taken is `Prog.d.tour = {done}` (merged as the earliest, in `KNOWN`) plus `playbook-tour` in localStorage; Settings → Take the tour again is `Tour.start(true)` and ends on the view it started from. Its classes use the `tw` prefix (`.tour` and `.tring` were taken). A feature a player should know about gets a step or a line in one; a step whose target can be hidden needs a `skip`. `e2e_tour.py` checks that the tour names every tab, every part of Your games, every setting (its `SETTINGS` map) and every feature in its `FEATURES` list.
- The last three games: `Review` in `product.js`, a part of Your games (`S.gseg === 'last'`, house and personal) with a pointer on the Drill page (`drillCard`). On the website it reads the newest games through `Recap.read` (`check`, at most every `RG_EVERY`, and Check now); any copy takes a pasted PGN (`add`, which asks for the side when neither player is the account). Three are kept in `d.rg.g` (newest `added` first; merged per game in `mergeProg`: what either copy worked out, the earliest `added`, the drill counts with more runs; `rd()` reads without creating the key, `st()` writes). Each review: `u` the moves, `at`/`by` where it left the lines in play (`walk`, over `inBook(s)`: the nodes on `BOOKS[s].lines`; `by` is `opp`, `me` or `end`), `ln` the engine's answer when the opponent left the book, `mk` the first move that lost 150 or more (depth 10, checked again at 14; `0` when there is none), `d` the drill runs (`o` and `m`: [runs, clean, last]). The engine part (`work`) runs only while the part is on screen and stops when it isn't, so it never takes the engine from a lesson. Drill it is drill kind `rv` (`fen0`, `moves`; `Review.fen`, `legal`, `tryRv`, `advance`, `panelHTML`), hooked into `dFen`, `legalFor`, `expectedMove`, `tryMove`, `renderDrillBoard`, `drillPanelHTML` and `renderDrill`; a review where the player left the book drills the book's line from move one (`drillBook`: a line drill that carries the review's id as `S.drill.rv`; the record wrapper counts it into `R.d.o` through `Review.drilled`, and its end panel leads back to the games) or opens the Sandbox there (`practise`). `Review.left()` lists the games where the player's own move left the book and the book's line (`bookLine(R)`, read from the book of the game's colour) hasn't been drilled clean since: `announce()` (after a check, and from `Coach.onView` everywhere but the reviews themselves) says each once with **Drill the line** on the bubble (`data-cgo="rvb:<id>"`; a bubble can carry a second button, `cta2`), `remind()` says the newest once a day on the Drill page, and `drillCard()` leads with it there. A test that counts chess.com reads holds the reviews back (`Review.tried` set in the future, as `e2e_recap.py` does): they read the same month from the same address.
- The Sandbox's side column has the openings, the odds and the session numbers; the start position is under the board (`#sbwhere`, `sbFromHTML`: a thumbnail, Change the position, Start from move one). The third number counts `sbPool()`: the drillable lines in the openings picked, or the ones through the start position. "What else … could play here" is a `details.xmore` whose state is `S.sbElse`.
- The Sandbox from a position: `SB_FROM[side]` (a node, for this visit only) is where games start (`sbStart` puts `D.from`, plays from there with scope `all`); `sbSetupStart` opens the set-up board (drill kind `sbset`: book moves for either side, `sbBookKids`, `sbLegal` for legal moves on the other side's turns, `pickable` for which pieces a tap picks up; `D.hist` the moves on the board and `D.fwd` the ones stepped back from, `sbSetJump`/`sbSetStep` behind the arrows under the board (`sbCtlHTML`), the arrow keys and a tap on a move in the list; the side panel is hidden while it is open). Practise from here in a lesson and in a review sets it too.
- Words the player reads go out as short bullets, not paragraphs: `bullets(text or array)` splits on sentences (`sentences`, `firstSentence`), and `Coach.say` takes an array or a multi-sentence string and draws bullets. A line or two at a time.
- There is no Learn tab: the `learn` view is an opening's page under Your games (`tabOf('learn') === 'games'`). Don't add it back to `VIEWS`. There is no cheat sheet tab either: the cards are `glanceHTML` on each opening's page, behind the Lessons | At a glance switch (`S.lview`), and `#cheat` opens that.
- Your games opens on one grid with a switch above it (`segHTML`, `S.gseg`): the house page in the template (`renderGames`: openings, missed shots, game reviews) and a player's own in `product.js` (`Product.games`: openings for both colours, where they leave the book, recent games). Both draw an opening as `openTile` (the cheat-sheet board, the record, the lines known). Keep it one part at a time.
- Reminder emails: `supabase/functions/nudge` (`index.ts` for Deno, `pick.js` the rules, `titles.json` written by `assemble.py`) and `supabase/nudge.sql`. Not deployed from here: the proxy blocks Supabase.
- `app/product.js` and `app/product.css` are the product shell: who is looking (`PERSONA`: house, new, ready), the welcome and locked screens, games in, the reading screen, findings, the would-you-rather cards (`CATALOG`, `STYLE`), the personal playbook (`applyProfile`) and the coach. `assemble.py` inlines all three files. `product.js` wraps `render`, `renderGames` and `Prog.record`, so it has to stay after them and before the boot code. A choice card offers up to four systems (`.duo`, `.duo.trio`, `.duo.quad`): the player's own first, then the ready ones in `CATALOG`'s order.
- New class names in `product.css` must not exist in the template's styles: `.opt`, `.locked`, `.ring`, `.field`, `.dots`, `.big`, `.who` and `.top` were all taken. Check with grep before adding one.
- The monthly recap: `Recap` in `product.js`, a part of Your games for the house playbook and a personal one (`segHTML` entries can carry a dot as a fifth element). It reads the account's month from chess.com or Lichess (only on the website: the claude.ai copy can't reach them), runs `Analyze.run` on it and keeps a summary per UTC month in `d.recap.m` (merged per month by `at`; `seen` and `chk` the latest). Checks: on opening and on Your games, at most every `RECAP_EVERY`; a failed check is kept on the page only. The house account is `HOUSE_ACCT` in the template, also the username that confirms a switch of system.
- The coach: `Coach` in `product.js`. `lineNote` writes the note in the drill panel when a line ends (`S.drill.slipAt` holds `[index, move]` for each slip; `Prog.record` counts them per move in the line's `sl`), `quizNote` the checkpoint's, `news` the once-a-day word per tab, `tap` what a tap on the coach says. Badges and today's five keep the bubble. Anything that wraps `Prog.record` must pass all its arguments on.
- After the course: `d.course.grad` (stamped once by `stampGrad`, merged as the earliest) turns the Course tab into a library. Deep dives are `DEEP` in `content/course.py`: each unit's optional lessons in parts, each lesson in exactly one part. `build_course.py` adds their boards and checkpoints (`deep`, `deepUnits` in `data_course.json`). In the template, parts sit in `UNIT` with `U.deep`, and `listOf(U)` gives a unit's siblings; use `unitNo` and `uword` (unit or part) in anything a unit and a part share. `renderGrad`, `renderLibrary`, `renderDeep` and `deepRank` (the coach's picks and their reasons) live in `app/product.js`. The text on a lesson board comes from the lesson at run time (`slideOf`), so a personal playbook gets the scrubbed words.
- Systems: `PACKS` in `content/black/bmeta.py` and, for White, in `content/white/content2_meta.py` (slot → packs → chapters). In the library: White `e4`, `d4` (the London), `flank` (the English); against the e-pawn `e5`, `caro`, `sicilian`, `scandi`; against the d-pawn `slav`, `kid` (two chapters, `kid` and `kidx`). The chapter `other` (White's other first moves) is in every Black pack. A new system is a content module like `content/black/bcaro.py` or `content/white/london.py`, a chapter in `CHAPTERS`/`CH_META` (for White, `CHAPTERS` is in `content2.py`), an entry in `PACKS`, cheat rows, a course unit and plans. A lesson's main line must pass through one of its chapter's roots (the Black build checks every lesson, the White build the lessons of its later packs). With a White pack other than the e-pawn in play, `applyPacks` moves `D.e4` to that pack's first move (the Sandbox plays it); `oddsRoot` stays on the e-pawn node. The page keeps only the packs in play (`applyPacks`, `PICKS`, `syncPacks`); `D.full` is the whole library and is what the game analysis reads. `tests/e2e_packs.py` covers the switch.
- Drafting a pack: `pipeline/draft.py` (not part of the build; needs the three engine paths). The scripts that drafted the Scandinavian, the King's Indian, the English and the odd lines are in `pipeline/drafts/` (the setup's order, the moves fixed by hand, the lessons, the notes); each rewrites its module in `content/`, and with `data/cache/draft_cache.json` reproduces it exactly, so change a note or a fixed move there and run it again, not in the module. `Walk(me, system, fixed, known, tol, thr, min_reach, depth, follow)` plays the other side by the Maia odds and yours as `fixed[path]`, then the move another order already gave this position (`known_from(side, skip_chapters)` for the book as built: skip the pack being redrafted), then the first move of `system(board, path)` within `tol` of the engine's best, then the engine's best (`flags` lists where the setup was overruled: those need a note). `emit(leaves, lessons, me)` writes the `L(...)` text (a lesson has a `root` or several `roots`, and `main=` to pick its main line), `named_moves` the named lines, `module_text` the file. Call `draft.done()` at the end of a script, never through `atexit` (the engine's quit hangs there). After a draft: build the book, `check_black.py 14 <parts>` or `check_white.py 14 <ids>` (with ids it checks any pack), fix a `LOSS` with a `fixed` entry and redraft. A build that fails an assertion can hang on the engine's exit the same way: kill it. `content/black/bodd.py` and `content/white/odd.py` are the odd first, second and third moves in the house chapters, drafted with the house book as `known`; a new first or second move there has to be added to its chapter's `roots` in `CH_META`.
- Plans: every line ends with one. `content/plans.py` has the written ones: `W`/`B` for each lesson's main line, `LW`/`LB` for side lines by line id. `pipeline/plan_lines.py` gives every other line one (`data/line_plans.json`): a side line ending on the same position as a planned main line takes that lesson's plan (`same`, attached as `ps`), the rest are read off the board and Stockfish's line from the end (`plan_pv.py`, depth 18, `data/cache/plan_cache.json`); lines ending in mate have none. A read-off bullet only states what the board or that line shows (pieces at home, castling, the engine's next pawn or piece move in words, the material, a king that can't castle, a pawn with no neighbour, the other side's next two moves); when one misses the point, write that line's plan in `LW`/`LB`. `assemble.py` attaches them (`plan` or `ps` on the line) and checks every plan for notation. In the template: `planOf(lineId)`, `planKick`, `planRef(side, lineId)` for the explore board; the card shows at the end of a line in study, after a clean drill, in every Sandbox report and on the explore board opened from there.
- Opening names: `data/openings` (lichess-org/chess-openings, CC0, unchanged) read by `pipeline/names.py`. The page carries the whole list (`page_table()`, `OPENINGS_RAW`, a hash of the position without move counters and with an en passant square only when the capture is legal) and names any position with `Openings` (`ofMoves`, `ofNode`, `startedBy`), lichess's way: the last named position on the way there. `opnHTML` shows it in study, line drills, the Sandbox and the explore board; the reviews add it to a move that starts a named line. `content/opening_names.py` puts real names in place of move descriptions (`LABELS` by the moves that reach a position, `TITLES` for lessons, `LINE_TITLES`, `PARTS`), applied at the end of both book builds (`names.apply`), which stop on a path or id that isn't in the book. `lc()` keeps a name's capitals (`NAMED`).
- `docs/engine/` is Stockfish.js 19 (GPL-3.0), unchanged release files. Keep its README and license next to it. `app/vendor/chess.js` (BSD-2) is inlined by `assemble.py`.
- Skill units (`threats`, `finish`, `endings`) share one item format in `data/course_*.json`; their wording is the `SKILL` table in the template. `pipeline/explain_skills.py` (needs Stockfish, not part of `make build`) fills `refute[move] = [reply, label, material won at once, the moves after it, material lost, engine number]` for every wrong move and `fine` (accepted moves that lose nothing) for the threat positions. `recut` and `regrade` redo the cutting and the grading without a full engine pass.

## House rules for the app

- The house playbook (the artifact build, and accounts with progress from before personal playbooks) must look and behave as before. Anything written for other players goes through `PERSONA`.
- The coach never speaks while a drill, practice game or checkpoint is being played, and never hints at a move. A badge earned then waits in `Badges.queue`. Play along is the one place the move is shown, by design: the arrow and the coach's card beside the board, never the bubble. The tour is the one place the coach leads the player through the app; while it runs the bubble stays quiet.
- A drill explains, but doesn't give the move away: the other side's move comes with its idea, and a slip with the answer that punishes it. The book's move is named only on the second miss, with the arrow.
- No game counts in what a new player reads about bringing games in ("connect your account"). The 200-game bar (`NEED` in `product.js`) is checked, not announced.
- One position, one move, inside every combination of packs a player can hold. If two move orders reach the same position, the book plays the same move in both. Before changing a line, look for the position in the other lessons (`lint_claims.py` reports the conflicting paths).
- One order per setup. The d-pawn setup comes out in the order given in the README ("One setup, one order"). Where a line has to leave that order, the note at that move says why.
- A label says only what is on the board. "Pin" needs a piece that can't or shouldn't move because of what is behind it; a bishop coming at a knight with a pawn behind it is "Bishop comes at your knight". "Guards" and "hits" are checked the same way.
- The repertoire is "your book" in what the player reads (not "your study", "the guide" or "your prep"), and nothing on the page is written for the house player alone unless it goes through `PERSONA`: there is no footer line about where the playbook came from. Your games has no header with a count of games: totals go out of date, and no text quotes one ("in your 76 with White"). A count the page shows is counted from the book on the page (the Sandbox's lines met: `sbPool()`), never written down.
- A real name before a description. Where an opening, a gambit or a named line has a name (`data/openings`), the tiles, parts, lesson and line titles and the other side's choices use it (`content/opening_names.py`); labels that explain a move ("Knight hits your e-pawn") stay. Every board in study, drills, the Sandbox and the explore board shows the position's opening name.
- The tour keeps up with the app. A change that adds a feature, or changes how one is used, updates `Tour.build` in the same change (a step, or a line in one), and `e2e_tour.py`'s `FEATURES` or `SETTINGS` when it brings a new word; that test fails when a tab, a part of Your games or a setting isn't named in the tour.
- No chess notation in anything the user reads. The squares f7 and f2 are the only exception. Arrow and move data inside the code is fine. This covers what the engine says too: its moves go through `moveWords`.
- Nothing is marked (inaccuracy, mistake, blunder, key move) while a drill, a practice game or a checkpoint is being played: a mark on the other side's move says there is something to find. Lessons show the marks; the Sandbox marks its list when the game is over.
- A move the player makes lands at once. Only the other side's reply slides.
- The engine never shows during a drill (Play along included), a practice game or a checkpoint. It comes on when they end, and it is always available in lessons and game reviews. In a skill unit's practice sets it opens per position once that position is answered.
- Engine numbers are from White's side for both colours (plus: White is better). Only the words are turned to the player's side.
- Every colour is a CSS token defined for both light and dark themes. Check phone width (390px) for sideways scrolling.
- Progress records are shared between the books, so line, puzzle and lesson ids must never collide (`assemble.py` asserts this).
- Record counts quoted in the course text come from all 200 games; the books' own stats come from the original 149.
